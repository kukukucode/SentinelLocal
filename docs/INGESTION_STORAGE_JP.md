# 取り込み・評価・ログ容量の修正

Windows PowerShell 5.1向けの開発中の変更です。公開済みの`v1.2.1-preview.1`には含まれません。実行時Versionは引き続き1.2.1です。配布物のmanifestとソースコミットで修正の有無を確認してください。

## 取得と評価

Sysmon有効時、Watcherは対象イベントを古い順に取得し、原本情報を`sysmon-events.jsonl`、イベント1のプロセス識別情報を`process-events.jsonl`へまとめて保存します。署名確認やスコア評価はこの経路で実行しません。

保存後、`state/sysmon-analysis/pending`へ評価用のXMLを原子的に公開し、最後に`sysmon-cursor.json`を更新します。記録失敗・容量不足では未保存分のソースカーソルを進めません。カーソル更新前の中断は再取得を生むことがあるため、計測は同じソースイベントを重複排除します。

Watcherは`Watcher.ps1 -AnalysisOnly`を別プロセスとして起動します。新しいScheduled Taskは追加しません。この評価プロセスは保存済みの作成情報を使い、PIDを再問い合わせして観測時の識別情報を置き換えません。応答要求には観測時のSHA256を引き継ぎます。ファイルが消えたことを正常な署名として扱いません。

評価は完了したイベントの位置を保存して、原則5秒の処理単位で継続します。応答要求に失敗したイベントは残して再試行します。処理途中のプロセス停止でも`processing`を再開します。ソースログ消去時は、消去前の未評価データより後に相関状態のリセットを適用します。

親Watcherの異常終了後は、実行ファイル・引数・PID・生成時刻を照合した既存の評価プロセスを引き継ぎます。進行が止まった所有プロセスは再起動し、更新時には親タスク停止を待ってから評価プロセスを止めます。再起動は少なくとも30秒間隔です。

評価待ちは既定で5,000イベント、XMLの総量は`min(64MiB, Resources.MaxLogFileMB)`までです。上限ではソース取得を保留し、データを削除して空きを作りません。Windowsイベントログの上書き前に滞留を解消する必要があります。単一の署名確認やイベントログ問い合わせに厳密な実行時間保証はありません。

署名の短期再利用は、書き換え・削除を拒否して開いた実ファイルのSHA256とフルパスに結び付けます。有効期間は15秒、最大256件です。パス・サイズ・更新時刻だけで有効な署名を再利用しません。ハッシュ計算自体の時間は必要です。

## 稼働と追従の判定

状態画面、`Check-SentinelLocal.ps1`、測定前診断、測定中のhealth sampleは、Sysmonの取得待ちと評価待ちを別々に表示・保存します。

| 項目 | 意味 |
| --- | --- |
| CheckedAt / CursorRecordId | 調査時刻と保存済みソース位置 |
| SourcePendingEvents | 対象イベントの取得待ち件数。1,000件取得時は下限値 |
| SourceCountIsLowerBound | 件数が下限値かどうか。記録番号の差は使わない |
| SourceOldestWaitSeconds | 最古の対象未取得イベントの待ち時間 |
| AnalysisPendingEvents / AnalysisBytes | 保存済みだが未評価の件数とキュー使用量 |
| AnalysisOldestWaitSeconds | 最古の未評価イベントの待ち時間 |
| IngestionEventsPerSecond / AnalysisEventsPerSecond | 直近バッチの処理速度。120秒以上古い・取得不能ならnull |

未処理が存在して待ち時間が120秒を超えると`Delayed`、ログ消去などの不連続は`Discontinuity`、アクセス不能・評価プロセス不明・古いHeartbeatなどは`Unverified`です。取得不能を0件と表示しません。対象未処理がなければ、最後のイベントが古くても静かな正常状態です。

IntegrityMonitorは異常をHIGHで記録し、同じ状態の通知を5分単位で抑えます。正常に戻ったら`SysmonBacklogRecovered`を記録します。警告の保存に失敗した場合は通知済みとして抑制しません。Heartbeatが正常でも`Delayed`等なら計測前の診断は合格しません。診断合格は検知性能の合格ではありません。

## 分割保存と保持

JSONLは既定で1ファイル64MiBになる前に、`<stream>.s000001.jsonl`のような変更しないセグメントへ移します。新しいアクティブログは前セグメントの末尾ハッシュを引き継ぎます。`state/log-chain/*.segments.json`に連番・サイズ・件数・SHA256・チェーンの両端・閉鎖時刻を保存します。

ローテーションと期限削除はトランザクションを残し、中断後に対応する状態を確認して復旧します。欠落、余分なセグメント、同じ長さの改変、連番不整合、reparse pathは検証失敗です。索引とチェックポイントは管理者/SYSTEMだけが書けるインストール先に保存します。管理者にすべてを書き換えられた場合の独立した証明にはなりません。

`Resources.MaxTotalLogMB`はJSONL全体の上限で既定512MiBです。旧設定に項目がなければ512MiBを使います。単独バッチがファイル上限を超える場合や、総容量・空きディスクの制限に達した場合は書き込みを拒否し、ソースカーソルを保持します。記録失敗はApplicationログのSentinelLocal / Event ID 1901でも通知を試みます。管理者は監査保全後に容量・保持方針を確認してください。

分割済みストリームの期限処理は、閉鎖から`MaxLogDays`を超えた連続した先頭セグメントだけを削除します。残す側に削除済み範囲の末尾ハッシュと連番を保持します。アクティブなセグメントや新しい閉鎖セグメントは、古いレコードを含んでいても残ります。まだ分割していない従来ログは、従来の先頭レコード単位の期限処理を使います。

未解決応答、failed要求、queued snapshotを容量確保のために自動削除しません。JSONLの512MiBには、証拠・キュー・索引・処理中の一時コピー・`events.log`・CSV・計測のTempコピーを含みません。ディスク全体の厳密な上限ではありません。証拠には別の容量設定があり、計測用コピーの保持・削除はIssue #11で追跡します。

監査出力は全セグメント・チェックポイント・索引をコピーし、コピーの検証を終えてから確定します。manifestには索引のSHA256も含めます。診断も短いコピー処理後にコピーを検証し、履歴全体の解析で稼働中のログロックを長時間占有しません。計測・3件観測・状態画面の末尾表示も分割ログを読みます。

## 検証範囲

Windows CIは、取得前後の障害、評価再試行、実際の評価プロセスの起動・引き継ぎ・再起動、静かなソース、消去、取得不能、分割・改変・同時書き込み・中断復旧・保持・総容量・監査コピーを試験します。実Sysmonの統合試験も取得と評価を分離した経路を使用します。実Defenderスキャンや実マルウェアを使う試験ではありません。

元の実PC試験は、Sysmon原本30/30、Sentinelへの120秒以内の保存0/30でした。この値を削除・上書きしません。変更後の同じ30試行と遅延の中央値・p95・最大値は実PCで再測定が必要です。Issue #6はその結果を確認するまで未完了です。検知率・誤検知率・検知時間・ATT&CK対応率は引き続き未測定です。
